# TG TOP — архитектура, риски и текущая стадия

**Статус на 26 августа 2026 года, после payout hardening release:** TG TOP — уже работающий Telegram Mini App с production-сайтом, двумя Telegram-ботами, рейтингом сообществ, внутренним балансом GRAM, ручной модерацией ботов и подключением TON-кошелька. Это **не прототип**. Production работает на Express 5.2.1; production dependency audit показывает **0 critical / 0 high / 0 moderate / 0 low**. Для исходящих TON-выплат запущен отдельный durable worker, но его broadcast намеренно выключен до controlled E2E-проверки с отдельным разрешением владельца.

> Главное правило развития: сначала безопасность денег и данных, затем надёжность сервисов, затем масштабирование и новые функции.

## 1. Карта системы простым языком

```text
Пользователь в Telegram
        │
        ▼
TG TOP Mini App — React интерфейс
  • TOP, карточки групп, кабинет, кошелёк, модерация
  • понятные данные и действия для владельца сообщества
        │ защищённые tRPC-запросы
        ▼
Сервер TG TOP — Express + tRPC
  • авторизация Telegram Mini App
  • правила рейтинга, GRAM, модерации, выводов и сделок
  • health endpoint, rate limit, security headers
        │
        ▼
MySQL / Drizzle
  • пользователи и баланс GRAM
  • сообщества, рейтинг, ставки, reward-кампании
  • intent-история платежей, Stars, сделки, модерация
        │                         │
        │                         ├────────► Isolated TON payout worker
        │                         │           • DB jobs, wallet lease, reconciliation
        │                         │           • единственный процесс с hot-wallet mnemonic
        │                         ├────────► TON Connect / TON API
        │                         │           • подключение кошелька
        │                         │           • депозиты и контролируемые выводы
        ▼                         │
Telegram Bot + Reserve Bot ◄──────┘
  • подключение групп
  • проверка прав и актуальной ссылки
  • статистика, вознаграждения, уведомления, Telegram Stars
        │
        ▼
VPS `/opt/tgtop`
  • `tgtop.service` — сайт и API
  • `tgtop-bot.service` — основной бот
  • `tgtop-bot-reserve.service` — резервный бот
  • `tgtop-payout-worker.service` — isolated финансовый worker
  • HTTPS / обратный прокси / release backups
```

| Блок | За что отвечает | Текущий статус |
|---|---|---|
| **Mini App** | Интерфейс TOP, карточки, кабинет, листинги, подключение TON | Работает; главный экран требует дальнейшей декомпозиции, потому что `Home.tsx` слишком большой. |
| **API** | Доступ, правила, операции с рейтингом и GRAM | Работает на Express 5.2.1; есть security headers, ограничение запросов и health endpoint. |
| **База** | Источник истины для денег, листингов, рейтинга и статусов | Работает; ставки усилены транзакционной защитой. |
| **Боты** | Telegram-права, группы, ссылки, статистика и уведомления | Работают в primary + reserve схеме. |
| **TON** | Подключение кошелька, депозитные/withdrawal-потоки | Очередь вынесена в БД, а signing — в отдельный worker. Broadcast по умолчанию выключен до controlled activation. |
| **VPS** | Production-развёртывание и четыре сервиса | Работает; release проверяет staged runtime, checksum, зависимости на VPS, backup и rollback. |

## 2. Какие реальные риски были найдены и уже закрыты

| Риск | Чем был опасен | Что сделано | Статус |
|---|---|---|---|
| **Одновременные ставки** | Два человека могли видеть одну старую цену; списание GRAM и новое место могли разойтись в редкой гонке. | Проверка цены, блокировка доски, списание GRAM, запись intent и перестроение рейтинга объединены в одну транзакцию. Цена для интерфейса формируется сервером. | **Закрыт P0** |
| **Dependency-уязвимости** | Старый dependency tree содержал critical/high/moderate/low advisories, включая Express 4 dependency chain. | Обновлены зависимости и выполнена отдельная migration на Express 5.2.1 с contract-тестами wildcard-маршрутов. Локальный production audit: **0 critical / 0 high / 0 moderate / 0 low**. | **Закрыт P0/P1** |
| **Несовпадение `dist` и runtime dependencies при VPS-релизе** | Новый код мог потребовать пакет, которого нет в production `node_modules`. | Введён единый staged release unit: `dist`, audited `node_modules`, manifest и lockfile активируются и откатываются вместе после проверки SHA-256, трёх сервисов и `/healthz`. | **Закрыт P1** |
| **HTTP-защита** | API не имел базового слоя заголовков, лимита частоты и публичного readiness-сигнала. | Добавлены security headers, rate limit для `/api/trpc` и `/healthz` с проверкой базы. | **Закрыт P0** |
| **Сбой базы выглядел как выход из аккаунта** | Валидный пользователь Telegram мог получать неясное состояние «не авторизован». | Для валидной Telegram-сессии сервер выдаёт понятную временную ошибку доступности, а не маскирует сбой под logout. | **Закрыт P0** |
| **Устаревшая ссылка «Перейти»** | Карточка могла вести на изменённый username или переставшую работать ссылку. | Сервер сверяет ссылку по chat ID через Telegram; при смене карточка снимается с TOP и владелец получает уведомление. | **Закрыт P0** |
| **TON-кошелёк другого Telegram-аккаунта** | В WebView мог сохраняться чужой wallet session. | Введена привязка session к владельцу Telegram, единый безопасный адрес и явное отключение. | **Закрыт P0** |
| **In-process очередь и доступ web/API к hot-wallet secret** | Рестарт мог потерять очередь, а публичный процесс не должен владеть ключом подписи. | Добавлены MySQL-backed payout jobs, wallet lease, bounded reconciliation и отдельный sandboxed worker. Mnemonic отсутствует у web и обоих bot services; worker активен, но broadcast выключен. | **Закрыт P0/P1** |
| **Минимальные ставки 0.1 GRAM** | Новая равная ставка могла оказаться в нижнем свободном месте. | Верхний свободный слот выбирается детерминированно; есть регрессии для равных ставок. | **Закрыт** |
| **Открытие групп по username** | Username в Telegram может быть перевязан на другой объект. | Переход идёт только после актуальной server-side проверки; private communities используют подтверждённые invite-ссылки. | **Закрыт** |

## 3. Что остаётся риском и почему это не надо делать «на скорую руку»

| Приоритет | Риск | Почему важен | Правильное действие |
|---|---|---|---|
| **P1** | Controlled activation исходящих TON-выплат ещё не проводилась. | Без реальной controlled E2E-проверки нельзя объявлять automated broadcast операционно готовым. | Оставить broadcast выключенным; перед включением согласовать точный test recipient и сумму, провести один контролируемый smoke и сверку chain. |
| **P1** | DDoS-ограничения пока application-level. | Bounded API rate limit и финансовые DB-барьеры есть, но они не заменяют edge WAF/NGINX limit zones. | Настроить reverse-proxy limit zones, request-size limits и мониторинг 429 до роста трафика. |
| **P1** | Telegram Stars: если лот меняется между оплатой и активацией, intent получает `refund_required`. | Нельзя считать такой платёж окончательно решённым без операционного refund-процесса. | Сделать отдельный контролируемый refund workflow и журнал оператора. |
| **P1** | Нет полного E2E-контура реального Telegram/TON/Stars. | Unit-тесты ловят регрессии кода, но не весь внешний путь. | Добавить production smoke-checklist и защищённый staging test account. |
| **P2** | `Home.tsx` содержит слишком много логики. | Небольшая UI-правка может задеть листинги, кошелёк, рейтинг и модерацию одновременно. | Разделить на доменные модули: ranking, group detail, wallet, moderation, workspace. |
| **P2** | Клиентский JavaScript около 2.8 MB до gzip. | Длиннее первый запуск Mini App, особенно на мобильной сети. | Code splitting: Wallet, Moderation, NFT, charts и тяжёлые Sheets подгружать по требованию. |
| **P2** | Наблюдаемость пока базовая. | После проблемы сложно быстро объяснить: сеть, база, бот, TON или пользовательский путь. | Добавить error IDs, structured logs, dashboard health и alerting по сервисам. |

## 4. На какой стадии продукт

| Слой | Оценка | Что это означает |
|---|---:|---|
| Каталог, TOP и модерация | **8/10** | Основной сценарий продукта есть и уже работает в production. |
| Telegram-интеграция | **7/10** | Основной и резервный бот есть; для следующего уровня нужны E2E-проверки и alerting. |
| Рейтинг и GRAM | **7/10** | Логика и транзакционная защита усилены; нужна нагрузочная проверка и мониторинг. |
| TON / деньги | **6/10** | Durable worker, lease, secret isolation и fail-closed controls в production; broadcast остаётся выключенным до controlled E2E smoke. |
| Качество кода | **6/10** | Хороший набор регрессий, но есть крупные монолиты и source-contract tests вместо части интеграционных. |
| Production-эксплуатация | **7/10** | Есть проверенный staged release, checksum, полный runtime rollback и owner runbook; всё ещё нужны monitoring, alerting и подлинный staging. |

> Итог: сейчас TG TOP находится на стадии **рабочего production MVP с усиленной безопасностью**. Следующий правильный этап — не добавлять десятки функций, а закрепить платёжную устойчивость, наблюдаемость и модульность. После этого новые направления — аналитика, NFT, аренда, сделки — будут развиваться быстрее и безопаснее.

## 5. Правильный порядок дальнейшей работы

1. **Провести controlled E2E smoke TON:** один заранее согласованный recipient/amount, chain reconciliation и rollback-plan; до него broadcast остаётся off.
2. **Добавить наблюдаемость:** error IDs, health всех четырёх сервисов, money intents и неудачные Telegram API вызовы.
3. **Усилить edge anti-DDoS:** reverse-proxy limits/WAF до увеличения публичного трафика.
4. **Разделить большой интерфейс на модули** без визуального rewrite.
5. **Ускорить Mini App:** code splitting и уменьшение первой загрузки.
6. После этого расширять пользовательские функции: аналитика, сделки, NFT и реферальная система.
